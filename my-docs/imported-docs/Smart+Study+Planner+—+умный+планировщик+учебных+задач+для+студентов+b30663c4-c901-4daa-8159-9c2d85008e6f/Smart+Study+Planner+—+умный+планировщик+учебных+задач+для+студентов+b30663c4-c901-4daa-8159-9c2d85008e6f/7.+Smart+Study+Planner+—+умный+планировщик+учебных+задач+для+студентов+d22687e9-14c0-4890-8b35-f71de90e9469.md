# **Задание 2. Проектирование API (OpenAPI)**

## **1. Подход к проектированию**

API построен в формате REST и соответствует **2 уровню зрелости Ричардсона**:

- используются ресурсы (`/tasks`, `/plans`, `/calendar`);

- применяются HTTP-методы (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`);

- отсутствует привязка к `current`, используется явная работа с периодами.

## **2. Основные сущности**

Используются следующие сущности:

- **User** - описывает пользователя системы.
Используется для отображения профиля, персонализации интерфейса и привязки всех данных (задач, планов) к конкретному пользователю.

- **Task** - основная единица работы пользователя.
Задачи отображаются на экране задач, участвуют в формировании плана и имеют приоритет, который влияет на алгоритм планирования.

- **Event** - события из календаря (например, пары, встречи).
Не являются задачами, но влияют на доступное время, поэтому используются при генерации плана.

- **Plan** - результат работы системы.
Представляет собой недельный план, который пользователь просматривает, сохраняет и редактирует.

- **PlanDay** - часть плана, разбивка по дням.
Нужна для корректного отображения на UI (недельный календарь) и удобного управления задачами внутри конкретного дня.

В моделях присутствуют:

1. **enum (приоритет задач)**

Использование `enum` для поля `priority`:

- ограничивает возможные значения (low, medium, high);

- исключает ошибки на фронте и бэке;

- упрощает сортировку и логику генерации плана.

1. **array (списки задач)**

Массивы используются:

- в списке задач (`TaskList`);

- в списке событий (`EventList`);

- внутри плана (несколько задач на день).

Это отражает реальную логику системы:
у пользователя всегда **несколько задач и событий**, а не один объект.

1. **вложенные объекты (Plan → days → tasks)**

Структура:

```Plain Text
Plan
 └── days[]
      └── tasks[]
```

Выбрана потому что:

- напрямую соответствует UI (неделя → дни → задачи);

- упрощает отображение на фронте (не нужно дополнительно группировать данные);

- позволяет легко редактировать конкретный день без переработки всего плана.

## **4. Обоснование использованных решений**

- Использован JWT (BearerAuth) для идентификации пользователя.

- Используется единая модель Plan с вложенной структурой.

- Полиморфизм (`oneOf`, `allOf`) не применялся, так как структура данных фиксированная.

- Параметры вынесены в query и body в соответствии с REST-практиками.
