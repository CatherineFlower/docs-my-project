# Хранение данных

## Сущности и характер данных

| Сущность | Основные атрибуты | Акторы | Характер данных |
|---|---|---|---|
| Пользователь | id, email, passwordHash, name, university, language, notificationsEnabled | пользователь, backend | транзакционные |
| Задача | id, userId, title, subject, priority, status, dueDate, estimatedDuration | пользователь, backend | транзакционные |
| Событие календаря | id, userId, title, location, startAt, endAt, type | пользователь, backend | транзакционные |
| План | id, userId, weekStartDate, progress, status | пользователь, backend | транзакционные |
| Запланированная задача | id, planId, taskId, date, startTime, endTime, orderIndex | пользователь, backend | транзакционные |
| Логи активности | id, userId, eventType, payload, createdAt | backend, аналитика | аналитические |

## Выбор технологии

Основные сущности системы имеют строгую структуру, внешние ключи, транзакции и высокие требования к консистентности. Поэтому для пользователей, задач, событий, планов и запланированных задач выбирается реляционная база данных.

Логи активности растут быстрее, имеют полуструктурированный payload и не требуют строгой транзакционности в основном пользовательском сценарии. Поэтому они могут храниться в аналитическом хранилище или отдельной таблице с последующим переносом в аналитический контур.

## Таблица выбора

| Критерий | Основные сущности | Activity logs |
|---|---|---|
| Тип данных | строгая структура | полуструктурированные данные |
| Связи | есть | минимальные |
| Транзакции | нужны | не критичны |
| Консистентность | высокая | допустима eventual consistency |
| Нагрузка | чтение и обновление | интенсивная запись |
| Итог | реляционная БД | аналитическое хранилище |

## Итоговое решение

Для MVP достаточно PostgreSQL как основного хранилища. Логи можно начать хранить в таблице `activity_logs`, но архитектурно отделять их от основной бизнес-модели, чтобы позже вынести в отдельное аналитическое хранилище.
